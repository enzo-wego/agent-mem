What went wrong

The linker ran for every message, but only thread roots carry a real summary

Everything ingested gets an embedding so search can find it. A thread root embeds its LLM-written, resource-aware summary — the thing topic linking was designed around. But every other Slack message embeds a heuristic stand-in: its first 200 characters of raw text.

The bug: after indexing any node, the pipeline enqueued the topic linker for it. So thousands of individual messages went hunting for "same topic" partners using raw text. Two bot posts or two similarly-phrased replies are nearly identical strings → cosine ≈ 1.0 → the LLM judge is shown two matching texts and answers "same topic, confidence 1.0". Technically correct for the words — worthless for the topic. That is precisely the shared-vocabulary noise this feature was built to eliminate, reborn one layer deeper.

Before — every message links

Raw-text messages match other raw-text messages on wording.

◉ thread root ──→ linked (summary) ├ message ──→ linked (raw text!) ├ message ──→ linked (raw text!) ├ bot reply ──→ linked (raw text!) └ message ──→ linked (raw text!)

After — the thread is the unit

Messages feed the root's summary; only the root links out.

◉ thread root ──→ linked (summary) ├ message ─┐ ├ message ├─ folded into the ├ bot reply │ root's summary └ message ─┘

The fix — commit 9ce09ab

One rule, enforced at three layers

Only two kinds of node may participate in topic linking: a Slack thread root embedding its resource-aware summary, and a non-Slack resource (Jira, PR, Confluence, doc, file). Raw-text Slack messages are excluded on every path in and out:

gatewherewhat it blocks
enqueueindex_artifact.goA freshly indexed message never queues a linking job in the first place.
sourcelink_topics.go · skipTopicLinkSourceJobs already queued for messages (or created by older code) exit as no-ops.
candidatelink_topics.go · shortlist SQLMessages can't be matched against either — and the adaptive cutoff (mean+2σ) is now computed over real summaries instead of a corpus dominated by message vectors.
why three gates, not one
Any single gate fixes the future; three make it unrepresentable. Old queued jobs, resynced jobs from other machines, and future callers of the linker all hit a wall regardless of which door they came through.
