What happens to a Slack message between arriving and getting a score

Every message hits eight checks before it becomes a node. Exactly one of them costs money, and it is the fifth. This is what it does, and which model it uses.

The short answer on the model

modelgoogle/gemini-embedding-001
notNo chat model. No Claude. No generate call. Embeddings only.
routeagent-mem → POST /embed on llm-gateway → OpenRouter /embeddings
width3072 dims (halfvec), GraphEmbeddingDims
task_typeDeliberately unset — OpenRouter rejects it, and a vector embedded with one lands in a different space than the stored corpus.
latency~200–500 ms. Plain HTTP, no subprocess, so it does not queue behind the gateway's 4-slot Claude semaphore.

That last row is the reason the design is embeddings and not a cheap-tier judge. A judge would spawn a Claude CLI subprocess per message and wait in the same queue that link_topics saturates during bursts, where p50 is 12.3 s. An embed is flat regardless of gateway load.

The path, cheapest check first

The order is the design. Each stage is cheaper than the one below it, so a message that can be dropped for free never reaches something that costs. Everything below happens inside one HTTP request: POST /api/graph/ingest/content, handled by internal/graph/handlers/ingest_content.go.

01
Collector posts the messagefree

Body plus metadata: channel_id, ts, thread_ts, author, subtype, attachments. thread_ts is present on arrival — the gate needs it later.

02
Derive node_idfree

buildNodeID(source, canonical_url, metadata). Deterministic, so a re-post of the same message resolves to the same node. A malformed request dies here with 400.

03
Deletion and DM guardsfree

A deleted upstream message soft-deletes our copy and returns. Any channel id starting with D is a direct message and is refused outright — DMs never enter the graph.

04
Per-channel filters1 db read

graph.channel_filters — an ignore-list plus keep/drop regexes. Purely mechanical, and it runs before anything with a model attached.

05
The eligibility gate1 embed, sometimes

This is where the score comes from. Four sub-steps, and three of the four exit before spending anything. Detailed below.

06
Alert-bot fingerprinting1 db read

Repeated machine alerts collapse into a fingerprint instead of becoming hundreds of near-identical nodes.

07
Upsert node and bodywrites

graph.nodes plus graph.artifact_bodies, and EnsurePerson for the author. From here the message exists.

08
Extraction, edges, follow-up jobsllm calls

Entity extraction, edge reconciliation, stale-edge pruning, attachment nodes, and enqueued describe_attachment work. This is the expensive tail the gate exists to protect.

Inside stage 5 — four sub-steps, in order

eligibilityGateSkip(), eligibility_gate.go:225. Read it as a series of escape hatches: only a message that falls through all three of the first ones gets embedded.

5a
Does the gate apply here?cached 60s

Config comes from settings['graph.eligibility_gate'], cached for 60 s. Exempt channels are excluded. An empty gated_channels means every channel is gated — not none, which is the opposite of what the name suggests.

5b
Have we already judged this exact message?1 indexed select

Lookup on (channel_id, message_ts) in graph.eligibility_decisions, newest first. If a decision exists, reuse it — no embed. This matters because ingest_content is invoked repeatedly for the same message: one message was scored 13 times across 6.5 minutes, another 6 times inside 3 seconds.

5c
Is this a reply under an eligible root?1 indexed select

If thread_ts is set and differs from ts, look up the root's decision. Root eligible → the reply inherits it, written as decision_source='inherited_root' with score = NULL, and no embed. Root missing or ineligible → fall through and score it normally; a thread can turn relevant, and a missing root is never read as a refusal.

5d
Score it1 embed

The only path that spends anything. Embed the body, cosine it against the scope vector, compare to two thresholds, write one audit row.

How the number is actually computed

the whole of it
scope = graph.topic_subscriptions[1].scope_definition // 1,524 chars scope_v = embed(scope) // cached, computed once msg_v = embed(req.Body) // per message score = dot(scope_v, msg_v) / (‖scope_v‖ · ‖msg_v‖) // plain cosine

There is no model judging relevance and no prompt. The score is the cosine of the angle between two vectors — the message, and a single 1,524-character description of what payments work is. Nothing else is consulted: not the channel, not the author, not the thread, not the time.

The scope vector is computed once, not per message

Cached under {subscription_id, scope_refreshed_at}. Editing the scope bumps scope_refreshed_at, which changes the key, evicts the old entry and forces a re-embed. Every audit row records the scope_version it was judged under, so a threshold is never calibrated across two different definitions of scope.

Then two thresholds, and a band in the middle

≥ 0.62
eligible — process it
0.45 – 0.62
uncertain — would ask a cheap LLM, but llm_adjudicate is off, so it defaults to eligible
≤ 0.45
ineligible — dropped, but only in enforce mode

Cosine is clamped to [-1, 1], and a zero-magnitude, NaN or infinite result is an error rather than a score — which, per the fail-open rule below, means the message is processed.

Why your 0.488 message scored 0.488

the honest answer

Because 0.488 is the floor, not a middling score. It is the lowest value the corpus has ever produced. Embedding cosine has a high floor — two unrelated English sentences rarely score near zero — and the asymmetry makes it worse: a 56-character message compared against a 1,524-character multi-topic document can never align sharply, so everything compresses toward the middle.

Read the number as a rank, not a probability. Across 324 scored messages the whole observed range is 0.4836 to 0.6644 — a span of 0.18. Off-topic banter sitting at 0.488 is the gate working: that message is at the bottom of everything it has ever seen.

Threads: one message in, whole thread by inheritance

The scorer only ever reads req.Body — one message, never the surrounding conversation. That would be a real problem on its own, because replies are short and context-free by nature. "thank you for the update" scored 0.5334; in enforce the gate would have kept the question and dropped the answer.

Inheritance fixes it without a second embed. A reply under an eligible root is eligible by lookup — exact rather than approximate, and free. The schema keeps the two kinds of row from ever being confused, so inherited rows cannot contaminate the score distribution used for calibration:

Every error path processes the message

This is the one invariant worth stating on its own. A gate that drops at ingest never creates the node, and nothing downstream recovers it — a false negative is permanent data loss, while a false positive wastes one LLM call. So the asymmetry is built in everywhere:

failurewhat happens
config unreadable or malformedgate does not apply; message processed
dedup or thread lookup errorslogged as failed open; message processed

/embed fails or times outerror; message processed

In practice this fires about once every 45 minutes, almost always context canceled on the embed POST, tracking the gateway's own ~3.5% /embed 502 rate. Every one of those failed in the safe direction.

Where calibration stands

Offline labelling of 31 distinct messages — 6 clearly in scope, 21 clearly out, 4 marginal — puts the usable boundary near 0.596, not the shipped 0.45. At that point every clearly in-scope message survives and 88% of the noise is dropped; precision is 67%, recall 100%. Given the cost asymmetry, that is the right shape of trade.

It is not yet safe to set. The conclusion rests on 6 positives, and 0.5965 is the lowest of them — a knife edge that one in-scope message at 0.58 would move. The plan is to let dry_run accumulate to roughly 30 in-scope samples first. Two things must also happen before enforce: gated_channels has to be populated, because empty means everything; and the thresholds have to be set from a distribution produced by the scoring that will actually be running.
