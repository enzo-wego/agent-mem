agent-mem — how the knowledge graph is built

From a Slack message (or Jira / GitHub / Confluence / …) to a cross-source graph of typed nodes and edges.
Everything that flows in becomes a node with a deterministic ID; references between things become typed edges. One graph spans all sources, so you can traverse message → ticket → PR → people. Heavy work (full bodies, embeddings, identity) happens asynchronously off a Postgres job queue.

1 · The data model

nodes things

Each artifact = one row in graph.nodes, keyed by a deterministic ID so the same thing always lands on the same node (idempotent).

slack:C05…:1782281414.679019 jira:PAY-2204 gh_pr:wego/payments#1960 cf:3962896432 person:…

edges relationships

A typed link in graph.edges between two nodes. Schema supports REFERENCES · PART_OF · MENTIONS · TOUCHES · REPLIES_TO · AUTHORED_BY · OWNED_BY.

Today essentially all populated edges are REFERENCES — e.g. a Slack message that mentions PAY-2204 → REFERENCES → jira:PAY-2204.

2 · Three ways content enters

push content

EnzoBot's Slack socket forwards each message, already normalized, to POST /api/graph/ingest/content with {source, canonical_url, body, metadata}. The hot path — 8 sources.

push URL

POST /api/graph/ingest/url — a pasted link is matched to a source, turned into a node, and enriched by jobs. The only way wegohub & claude_artifact enter (claude.ai & Wego Hub links).

pull backfill

Jobs fetch full content from each source's API and run it through agent-mem's own normalizer/{slack,jira,…}.go to parse mentions, links and structure.

3 · What one ingest does

1
Derive node ID
buildNodeID() — deterministic per source (e.g. slack:<channel>:<ts>). Same input → same node.
2
Resolve author → person
identity.EnsurePerson() — the author (and mentions) become graph.people, deduped across slack uid / jira uid / gh login into one person.
3
Upsert the node (with a freshness guard)
upsertNodeOutcome() returns created / updated / unchanged. An older edit can't clobber a newer one: WHERE EXCLUDED.body_ts >= nodes.body_ts. Sets scope = slack:<channel> (what the map counts).
4
Store the body
Written into the 3 storage tiers (see §5).
5
Extract references → reconcile edges
The extractor finds links/IDs/entities and upserts edges; stale edges are pruned (see §4).
6
Register attachments
Each file → a slack_file node + a REFERENCES edge + a describe_attachment job (OCR / Gemini description).
7
Enqueue async enrichment
fetch_body (priority 0), resolve_identity (if the author has no email yet), plus the attachment jobs — all off the queue (see §6).

4 · How relationships form — the extractor

The extractor scans the normalized body three ways and emits Findings, each pointing at a target node with a suggested edge kind:

url

URL regex → links to Jira / PR / Confluence / Datadog / etc.

id_regex

Bare keys like PAY-2204, wego/payments#1960.

entity

Alias match against graph.entities (cached trie, 5-min TTL) — features, partners, currencies.

▼
body→ Findings→ reconcileEdges (upsert)+ pruneStaleEdges (delete)
Edges are reconciled on every revision: editing a message adds edges it now implies and removes ones it no longer does. The target node is auto-created as a stub even if that Jira ticket / PR was never ingested — backfill fills it in later.

5 · Body storage — 3 tiers (cost-managed)

graph.nodes.body
Normalized plain text — the hot tier, always present.
hot
graph.artifact_bodies
Full body / OCR / attachment descriptions. Has an expires_at TTL so bulk can age out.
warm
graph.artifact_index
Summary + 768-dim Gemini embedding for semantic search. The expensive tier (~9 KB/row + HNSW index), written by the index_artifact job.
cold

6 · Async enrichment — a Postgres job queue

Ingest returns fast; the heavy work is queued in graph.jobs and run by workers with priorities (0 = urgent).

JobPriorityWhat it does
fetch_body0Pull full content from the source API, re-normalize, re-extract.
index_artifact5Summarize + compute the Gemini embedding for search.
describe_attachment5OCR / Gemini-describe images & files.
resolve_identity5Backfill a person's email / identity across systems.
refresh_slack_users · refresh_slack_groups5Populate name lookups (the group one needs the Slack usergroups:read scope).

7 · End to end

Slack msg→ /ingest/content→ node slack:CH:TS→ author → person→ 3-tier body
↳
extractor→ edges → jira / PR / entities→ jobs: full body · embedding · OCR · identity
The result is one cross-source graph. It powers /resolve (context for a question), semantic /search, and the map panel's thread grouping & reference chips.
